# ADR 0001 — A hand-written corpus and a synonymy-only lexicon

**Status:** accepted

## Context

The project measures how often a semantic cache returns the wrong answer. That
requires knowing the right answer, which requires labelled data with a specific
and unusual property: it must contain many pairs of queries that are *lexically
close but semantically different*. Public intent-classification datasets are
built to be separable — that is what makes them useful benchmarks — so they
contain almost none of the pairs this study is about.

Two options:

1. Use a public dataset and synthesise confusable pairs by perturbation.
2. Write and label the corpus by hand.

## Decision

Write it by hand: 170 queries, 53 intents, 19 confusable families, 3 tenants.

Perturbation was rejected because it decides the answer. If confusable pairs are
generated by "take a query and swap one entity", then the finding that "a single
swapped entity is invisible to a pooled vector" is a description of the
generator, not of the encoder. The pairs have to be things a person would
actually type.

The families are the point. Each one isolates a different *kind* of decisive
token:

| family | what distinguishes the members |
|--------|-------------------------------|
| shipping-to-{DE,FR,UK,IE,US} | a proper noun |
| limits-on-{free,pro,enterprise} | a plan name |
| {enable,disable}-2fa | polarity |
| {import,export}-data | direction |
| error-{401,403,429,500} | a numeric code |
| {upgrade,downgrade}-plan | direction on a scalar |
| {add,remove}-teammate | polarity on a different noun |

A finding that held for only one of these would be a quirk. A finding that holds
across all of them is about pooling.

### The tenant trap

Three intents are worded **byte-identically** across `acme`, `globex` and
`initech` with three different correct answers. No encoder can separate them —
the inputs are the same bytes. They exist to make one point precisely: some
correctness problems are not similarity problems, and no amount of model quality
will fix them. Only scoping will. This is what section 4 of the report measures.

## The lexicon, and the test that nearly did not exist

`internal/embed` needs synonymy — "money back" and "refund" should be close, or
the study is about string overlap rather than meaning. With no embedding API
available, that synonymy has to come from a hand-authored table.

This is the study's largest integrity risk. A hand-written table that maps
`germany → country-de` and `france → country-fr` would separate the shipping
family *by hand*, and the report's central finding would be a description of the
author's table.

The obvious guard is a test asserting that decisive tokens never appear in the
lexicon. It was written, and it **failed** — on `activate → enable`,
`upload → import`, `bigger → upgrade`. Those are legitimate synonymy; the
decisive token is the *canonical form*, which is the whole point.

The property had to be stated more carefully, and the precision was worth more
than the original test:

**Class A — tokens with no legitimate synonym at all.** Entities, plan names,
HTTP status codes, tenant names, polarity particles (`on`, `off`, `not`). A
proper noun means itself. Any lexicon entry touching one, on either side, is the
author telling the embedder the answer. `TestNoLexiconEntryTouchesAnIrreducibleToken`
forbids it.

**Class B — tokens that may be canonical forms but must never collapse with a
family sibling.** `activate → enable` is fine. `remove → disable` is not,
because it merges the `add/remove-teammate` family into the `enable/disable-2fa`
family. `TestFamilySiblingsNeverCollapseToTheSameConcept` forbids it.

**That second test found a real bug on its first run: the table did contain
`remove → disable`.** It had been written without noticing that "remove" belongs
to a different family than "disable", and it was manufacturing exactly the
confusion the project claims to measure. Had it survived, section 1 would have
reported an inflated confusable-collision rate caused by the instrument.

A third test applies the same rule to the multi-word phrase table, matching on
whole words — an earlier version used `strings.Contains` and false-positived on
`"sub processors" → "subprocessor"` containing the substring `pro`.

## Consequences

- Every intent label is trustworthy, which is what makes precision measurable at
  all.
- 170 documents is far too few for a realistic IDF distribution. Section 3
  reports this as a finding rather than hiding it, because it is what happens to
  anyone computing IDF over their own corpus.
- The lexicon remains a hand-built component inside the measurement instrument.
  The two tests constrain it; they cannot prove the absence of subtler bias. The
  table is small and readable, and the README says to read it.
- The corpus cannot be swapped for a public dataset without losing the confusable
  families, which is the whole experiment.
