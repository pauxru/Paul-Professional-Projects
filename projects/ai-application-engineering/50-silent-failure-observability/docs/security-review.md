# Security and privacy review

This project runs offline against synthetic data, so it has no attack surface worth
enumerating. The review that matters is of the *design it argues for*: a monitoring system
that reads model output. That design has a privacy problem, and the problem is easy to talk
your way past.

## The claim to be careful about: "we only store embeddings"

Every drift detector here consumes vectors. It is tempting to conclude that a production
deployment can ship embeddings to the monitoring store and leave the text in the
application, and that this makes the monitoring store non-sensitive.

**Embeddings are not anonymisation.** They are a lossy, invertible-in-practice encoding.

- Embedding inversion is a solved research problem for sentence encoders: a decoder trained
  against the same embedding model reconstructs a large fraction of the original text from
  the vector alone, and needs only query access to the encoder to be trained.
- Even without inversion, a vector supports nearest-neighbour lookup. If an attacker can
  embed candidate strings, they can test membership: "is there a turn in this store whose
  embedding is within ε of `embed('my policy number is 4417...')`". That is a
  confirmation oracle over the underlying corpus.
- Vectors are stable across time, which makes them linkable. The same user asking the same
  question on two days produces two near-identical vectors, so an embedding store supports
  re-identification by correlation even when no identifier is present.

The correct posture is that **an embedding of personal data is personal data**, and the
monitoring store inherits the classification, retention limit, deletion obligation, access
control and residency requirement of the text it was derived from. Under GDPR it is
pseudonymised, not anonymised, and pseudonymised data is in scope.

The hashing trick used in this project happens to be *harder* to invert than a learned
encoder — there is no decoder to train and the hash is one-way — but it leaks in the other
direction: it is a bag of character n-grams, so a dictionary attack over candidate strings
recovers exact membership trivially, and rare n-grams (an account number, a surname) are
individually testable. It is not a privacy control either. Nothing about "we embed it"
is a privacy control.

## Consequences for a real deployment

1. **Do not store raw answers in the monitoring path if you can avoid it.** The detectors
   in this project need only the vector and, for the canary, a quality score. Store those;
   keep text in the application store with its existing controls, and join by ID when a
   human investigates.
2. **Give the monitoring store the same deletion path as the primary store.** A
   right-to-erasure request that deletes the transcript and leaves the embedding has not
   been honoured. This is the requirement most often missed, because the monitoring store is
   usually owned by a different team.
3. **Access-control the dashboard.** `sliced_output_psi` reports per-topic statistics; on a
   low-traffic slice, "the `warranty` slice moved" plus `MIN_SLICE = 8` is a statement about
   a handful of identifiable conversations. Aggregates over small denominators are not
   aggregate.
4. **Set a retention limit shorter than the primary store's, not longer.** The reference
   window here is 30 days. Monitoring rarely needs more, and unbounded retention of
   "just vectors" is how a monitoring store becomes the largest copy of the corpus in the
   organisation.
5. **Treat the quality canary's calls as production traffic.** Its 24 daily calls send real
   prompts to the model provider on a schedule; if the golden set was built from real
   customer questions, it is a standing, automated export of customer data to a third party.
   Golden sets should be synthetic or explicitly cleared.

## This repository specifically

- No network calls, no credentials, no environment variables, no third-party services.
  `test.ps1` asserts this: `node_modules` must not exist, the dashboard HTML must contain no
  `<script>` and no `http(s)://`, and Python imports (extracted by parsing, not grepping)
  must be numpy and pytest only.
- A secrets scan over all 28 tracked files runs as stage 7 of `test.ps1`, with production
  code held to a stricter pattern set than tests.
- All text is generated by `corpus.py` from fixed templates. There is no real customer data
  in the repository and no path by which any could enter.
