# What a clean test file proves

Nothing. That is the whole finding, and it took building the generator twice to
see it clearly.

## The first version was useless and passed everything

The obvious way to test a record decoder is to generate records, decode them, and
check the values come back. I wrote that. It passed. I then wrote the round-trip
test — generate, decode, re-encode, compare bytes — and it passed too, on every
seed, immediately.

I was pleased for about ten minutes.

The generator was calling `encode_record`. So the round-trip test was checking
that `encode_record` is a left inverse of `decode_record`: that the two functions
agree with each other. If both shared a misunderstanding — say, about how many
bytes a nine-digit COMP-3 field occupies — the test would agree with itself
forever and the first real file would be shredded.

So the generator was rewritten to lay out bytes itself, walking the field tree
with its own cursor and calling the low-level `numeric.encode_*` primitives
directly. It now asserts its own output length against `record_length()` —
computed by the copybook layout engine, a completely separate code path — and
raises if they disagree. There is duplicated layout logic in this repository and
it is load-bearing.

## The second version was still useless, for a better reason

With an independent generator, the round trip is a real test. It still passed
instantly, and the *naive* re-emission path — the one that writes each value in
the encoder's preferred form, throwing away how it was originally written —
passed too.

Of course it did. The generator emitted canonical encodings, because canonical
encodings are what an encoder produces. Every sign nibble was `0xC` or `0xD`.
Every field was fully populated with digits. There was no negative zero, because
why would you write one.

Real files are not like that. Thirty years of production data contains:

- COMP-3 sign nibbles `0xA`, `0xB` and `0xE` — legal alternates that some
  compilers and a lot of hand-written assembler emit
- zoned positives with zone `0xF` instead of `0xC`, from programs that `MOVE`d an
  unsigned value into a signed field
- fields full of EBCDIC `0x40` where uninitialised working storage was written to
  disk
- negative zero, which is `0x0D` and reads as `0`

None of those are corrupt. All of them decode correctly. All of them re-encode to
*different bytes* if you stored only the value.

So `Corruption` was added: explicit rates at which the generator emits each of
these. That is when the naive path finally failed, and it failed hard — 3,026 of
5,000 records rewritten, with zero numeric values changed.

## The measurement that makes the point

Section 8 of [`docs/results.md`](../results.md) runs the identical naive
re-emission against 1,000 records generated with `Corruption.none()`:

```
byte-identical = True
```

Same code. Same test. Clean corpus, passes. Dirty corpus, 60.5% of records
rewritten.

That clean corpus is exactly the test file a migration team writes for itself. It
is generated by their own encoder, so it contains only what their own encoder
produces, so it can only ever confirm that their encoder is self-consistent. The
bug is not in the code. The bug is in the shape of the test data, and it is
invisible from inside the project.

## The general version

I have started treating this as a checklist question on any data-migration work:

> *Where did the test corpus come from, and could it contain a case the new code
> gets wrong?*

If the corpus was generated by the system under test, or by a component that
shares assumptions with it, the answer is no — and the test suite is measuring
its own reflection. The fix is either real production data (usually impossible
for good reasons) or a generator written deliberately against the *format
specification* rather than against the implementation, with the awkward cases
turned on by default.

The second option is cheaper than it sounds and it is the only one that scales.
