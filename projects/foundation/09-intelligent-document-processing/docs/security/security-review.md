# Security Review — Intelligent Document Processing Platform

## Scope and method

A design-level security review of the platform as built in this repository: ingestion, pipeline,
review, export, persistence and the HTTP API. The method is asset identification → trust-boundary
mapping → STRIDE threat modelling per boundary → mitigations → residual risk. It is a self-directed
engineering review, not a penetration test. Emphasis is placed on the five risks that dominate a
document-processing system: **untrusted file handling, path traversal, SSRF on the export path, PII in
documents, and CSV/formula injection on export.**

## Assets

- **Document content** — supplier invoices/POs/delivery notes; may embed business and personal data.
- **Extracted fields & corrections** — financial values and reviewer actions that gate payment.
- **Master data** — suppliers, tax ids, bank account references.
- **Export records & ERP bookings** — the instructions that ultimately move money downstream.
- **Audit trail** — actor/action/resource records with before/after hashes.
- **Signing key** — the JWT HS256 key that authenticates all privileged API calls.

## Trust boundaries

1. **Client → API** — untrusted HTTP callers (uploads, review actions, queries).
2. **Drop folder → Ingestion** — files arriving on disk from an external process.
3. **API/Application → Object store** — file bytes written/read by generated keys.
4. **Application → Simulated ERP endpoint** — an outbound HTTP call to a configured URL.
5. **Application → Database** — persisted domain state.
6. **Reviewer → Review console** — browser-rendered evidence and edit actions.

## Data classification

| Data | Classification | Handling |
| --- | --- | --- |
| Document body / word boxes | Confidential (may contain PII) | AuthN required; not written to logs; stored by opaque key |
| Extracted financial fields | Confidential | AuthN + policy; shown only to authorised reviewers |
| Supplier tax id / bank ref | Confidential | Master-data access authenticated; format-validated |
| JWT signing key | Secret | From config/env only; never committed; Production guard on default |
| Audit records | Internal, integrity-sensitive | Append-only; before/after hashes |
| STP / metrics | Internal | Aggregate only; no document content |

## Threat model (STRIDE per boundary)

| Boundary | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| Client → API | Forged caller | Mutated request/field | Denied action | Read others' documents | Upload flood / huge file | Call privileged endpoint |
| Drop folder → Ingestion | Malicious file source | Path-traversal filename, zip/oversized | — | — | Disk-fill via large/many files | Executable content |
| App → Object store | — | Overwrite via crafted key | — | Read arbitrary path | — | Escape storage root |
| App → ERP endpoint | Spoofed target | Tampered payload | — | Data exfil to attacker URL (SSRF) | Retry storm | — |
| App → Database | — | SQL injection | — | Cross-record read | Unbounded query | — |
| Reviewer → console | Session theft | CSV/formula injection in export | Unattributed edit | Evidence leakage | — | Approve without permission |

## Mitigations implemented

- **Untrusted file handling:** upload endpoints enforce a **content-type allow-list** and a **size
  cap**; oversized or wrong-type uploads are rejected with `400` ProblemDetails. Content is **hashed**
  (duplicate detection) and **never executed or interpreted as code**. Files are stored under
  server-generated keys, not client filenames.
- **Path traversal:** object-store keys are generated by the application (document id/version based),
  and the `LocalFileSystemObjectStore` resolves and confirms every path stays **within the configured
  storage root**, rejecting keys that escape it. Client-supplied filenames are treated as metadata
  only.
- **SSRF on export:** the default `IErpExportClient` is an **in-process** simulated client that books
  through `SimulatedErpLedger` and makes **no outbound network call**, so there is no live SSRF
  surface in the default configuration. The `ErpEndpoint` value is server-side configuration that a
  real HTTP export adapter would use; the review flags that such an adapter **must** validate the
  destination (host/port allow-list, block link-local/metadata `169.254.169.254`, enforce TLS) before
  sending — this is called out as a production item below.
- **PII in documents:** access to document bodies and fields is **authenticated and policy-gated**;
  request logging records metadata and correlation ids but **not document contents**; the review
  console shows evidence only to authorised reviewers.
- **CSV / formula injection:** `ErpPayloadBuilder.Csv` prefixes any value beginning with `= + - @`
  (or tab/CR) with a single quote, neutralising spreadsheet formula execution when an exported CSV is
  opened. Unit-tested (`ExportServiceTests` CSV-injection cases).
- **AuthN/Z:** JWT bearer with four **policy-based** permissions (`documents:submit`,
  `review:process`, `review:approve`, `export:manage`); missing/invalid token → `401`, insufficient
  permission → `403`. The dev-token endpoint is mapped **only in Development**; startup **refuses the
  default signing key in Production**.
- **Tampering/repudiation:** the pipeline is an audited **state machine**; state-changing actions
  append `PipelineTransition`/`AuditEntry` records with actor, correlation id and before/after hashes;
  corrections capture reviewer, reason and timestamp.
- **DoS:** framework **rate limiting**, request-size caps and bounded queries; export uses **bounded
  retries** then dead-letters rather than looping.
- **Injection (SQL):** all persistence goes through EF Core parameterised queries; no string-built
  SQL.
- **Transport & headers:** security-headers middleware; ProblemDetails for uniform errors;
  correlation ids on every request.

## Residual risk

- The synthetic pipeline does not parse real PDF/Office files, so parser-level exploits (malicious
  PDFs, macro documents) are **out of scope** here and would need hardening with a real parser.
- The default export path makes no outbound HTTP call (in-process simulated ERP), so SSRF is latent
  rather than live; a real HTTP export adapter would need a strict destination allow-list with
  metadata/link-local blocking, which is a production item not implemented in this prototype.
- The local object store and file drop folder assume a trusted host filesystem; multi-tenant
  isolation of stored bytes is not implemented.
- Rate-limit and size-cap values are demo defaults and would be tuned per deployment.

## What would change for a real production deployment

- Replace the dev HS256 token issuer with **OIDC/JWKS** (e.g. Entra ID) and rotate keys via a secret
  manager (Key Vault); never a static key.
- Put the object store on **Azure Blob** with private endpoints and server-side encryption; scan
  uploads with anti-malware before processing.
- Harden export SSRF defence: strict host/port allow-list, block RFC1918/link-local/169.254.169.254,
  enforce TLS, and use a dedicated egress proxy.
- Add tenant isolation (EF global query filters + write-path assertions) and field-level log
  redaction; formalise PII retention/erasure.
- Centralised audit sink, alerting on dead-letter growth and authz denials, and WAF/CDN in front of
  the API.

## Explicit non-claims

This is a self-directed engineering demonstration. **No formal security audit, penetration test, or
compliance certification (PCI DSS, SOC 2, HIPAA, ISO 27001) has been performed or is claimed.** All
data is synthetic and fictional; no real secrets, personal data, suppliers, or bank details are
present in the repository. Signing keys in configuration are development-only placeholders.
