# ADR-005 — Unsubscribe token design

## Context

Every marketing message should carry a one-click unsubscribe link. Users
must be able to unsubscribe without logging in. The token must be tamper
evident, must expire, and must resist replay.

## Options

1. **Raw recipient id in the URL.** Trivial forgery.
2. **Random opaque token stored in the DB.** Requires a DB round-trip and
   token cleanup.
3. **Signed token with an HMAC and an expiry.** Stateless verification.
4. **JWT.** Overkill for a link.

## Decision

Adopt **option 3**: signed tokens generated by `UnsubscribeTokenService`:

- Payload: `tenantId | recipientExternalId | category | expUnix`.
- Signature: `hex(hmac_sha256(key, payload))`.
- Encoding: URL-safe base64 of `payload.signature`.

Verification checks:

- decodes without error,
- signature matches under constant-time comparison,
- expiry is in the future according to the injected clock.

## Consequences

- Stateless — no DB write on issue.
- Tamper evident — flipping any bit changes the signature.
- Expiring — abandoned links become invalid without cleanup work.
- Trivially inspectable in tests (`SecurityServiceTests`).

## Risks

- Key rotation is a manual redeploy in this implementation. Future
  improvement: allow a small set of trusted keys and rotate.
- Multi-use tokens can be replayed until they expire. If we need one-shot
  tokens the design gains a nonce column and a lookup on redeem.

## Alternatives revisited

If we ever need immediate revocation, we add a revocation table and check
it on redeem. Cost: one indexed DB read per click.
